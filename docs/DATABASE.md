# Database

Proposal for Part 5 of `docs/PLAN.md`. The machine-readable version is
`docs/database-schema.json`. Nothing here is implemented yet - Part 6 builds it.

SQLite through `node:sqlite`, one file at `data/kanban.db`, created and seeded
on first run. In the container that path sits on the named `kanban-data` volume,
which is what makes the board survive a rebuild.

## Shape

```
users
  id, username

boards
  id, user_id -> users.id, name, subtitle

board_columns
  id, board_id -> boards.id, title, position

cards
  id, column_id -> board_columns.id, title, details, position

messages
  id, board_id -> boards.id, role, content
```

Deletes cascade down the chain, so removing a board takes its columns, its
cards, and its chat history with it.

## Why relational rather than a JSON blob

A single JSON column per board would map one-to-one onto the Flutter models and
would be less code. It was rejected because of what the AI feature needs.

From Part 9 the model returns card-level operations - create this card, move
that one, rename that column. Applying those against a blob means read the whole
board, parse it, mutate it in memory, and write it all back. Two things go wrong
there. Concurrent writes silently clobber each other, because the last writer
wins with a stale copy of everything it did not touch. And a partially valid
batch is hard to reject cleanly, since there is no statement boundary to roll
back to - you have already built the new document in memory.

With tables, each operation is one statement, a batch is one transaction, and an
invalid operation aborts the batch without a partial write. That is the property
Part 9's tests are written against.

The cost is real: reading the board is a three-table read that has to be
assembled into nested JSON, and every card write needs a position reindex. Both
are contained in `db/index.js` and the board routes.

## Ids

`board_columns.id` and `cards.id` are TEXT holding uuid v4. `users.id` and
`boards.id` are ordinary INTEGER primary keys.

Column and card ids are text because the same id travels through the API, into
the Flutter models, out to the AI in the board JSON, and back in the AI's
response. A stable opaque string is the simplest thing that survives that round
trip, and it matches what the frontend already does - `BoardViewModel.addCard`
generates a uuid today.

The readable ids the frontend currently hardcodes (`todo`, `in-progress`) cannot
become primary keys. They are only unique within one board, so two users with a
To Do column would collide on insert. Scoping them per board would mean a
composite key that `cards.column_id` then has to carry as well, which is more
machinery than a uuid costs.

Ids are generated by the backend, never accepted from the client.

## Ordering

Card order within a column is an INTEGER `position`, contiguous from 0. Column
order within a board works the same way, though nothing changes it after the
seed since columns cannot be reordered in the MVP.

Contiguity is upheld by application code inside a transaction, not by a
constraint. A `UNIQUE (column_id, position)` index looks like the obvious way to
enforce it and is a trap: reindexing shifts several rows with one UPDATE, and
SQLite checks uniqueness as each row is written, so a shift that has not
finished yet trips the constraint depending on the order rows happen to be
visited. The index on `(column_id, position)` is therefore for lookup only.

A move is: remove the card from its old column's ordering, close the gap,
open a gap at the target index in the new column, write the card there. Same
column and cross column moves both go through it, in one transaction.

Fractional or gapped positions - 10, 20, 30, insert at 15 - were considered and
rejected. They avoid the reindex but need periodic renormalisation, and the
board is small enough that rewriting a column's positions is a handful of rows.

## Chat history

`messages` hangs off `boards`, not `users`, because a conversation is about a
particular board and Part 9 replays it alongside that board's JSON. Rows are
read `ORDER BY id`; the integer primary key already gives insertion order, so
there is no separate timestamp.

`role` is constrained to `user` or `assistant`. The system prompt is built fresh
on every call and is not stored.

## Multiple users

The MVP signs in one hardcoded account and seeds one board, but nothing in the
schema assumes that. Users are rows, boards belong to users, and every query
resolves the board from the signed in user rather than from a board id supplied
by the client. Adding a second user is an insert.

What is deliberately absent is any notion of a password. Credentials are checked
in the login route against constants. A `password_hash` column sitting unused
would suggest an authentication story that does not exist.

## What is not here

- **Timestamps.** No `created_at` or `updated_at` anywhere. Nothing in the API
  surface or the UI reads them, card order comes from `position`, and message
  order comes from `id`. This is the decision most likely to be worth
  reversing - if you want them, say so now, since adding columns later means a
  migration and there is no migration story in the MVP.
- **A migrations table.** The schema is applied with `CREATE TABLE IF NOT
  EXISTS` on every start. Changing the shape after data exists means deleting
  `data/kanban.db`, or clearing the `kanban-data` volume in the container.
- **Soft deletes, archiving, labels, due dates, assignees.** None are in the
  requirements.
- **A unique constraint tying one board to one user.** True for the MVP, but
  constraining it makes a second board a migration instead of an insert.

## Seed

Applied on first run only, detected by the `users` table being empty:

- one user, `user`
- one board, `Product Roadmap` / `Q4 delivery board`
- five columns: To Do, In Progress, Review, Blocked, Done at positions 0 to 4
- the six demo cards currently in `frontend/lib/data/dummy_data.dart`

Seeding the demo cards keeps the first run looking like the app does today, so
Part 7 swapping the frontend onto the API is not also a visible content change.
Dropping them to start with an empty board is a one-line change if you prefer.

## Foreign keys

`PRAGMA foreign_keys = ON` is set on every connection. SQLite defaults it off,
per connection, so the cascades above simply would not happen without it. Part 6
has a test that deleting a board removes its columns and cards, which is what
catches it if the pragma is ever dropped.
